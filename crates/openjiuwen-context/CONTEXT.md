# openjiuwen-context

## Intent

Owns the seam between the messages an agent accumulates and the payload sent to a model: conversation history, window assembly, token accounting, provider-window resolution, the compression/offload pipeline, and the observability of both.
Ports the public behavior of `openjiuwen/core/context_engine/` — `ModelContext`, `ContextEngine`, the processor family, the token registry and artefact manager, token counters, offload storage, compression recall, the session-memory boundary, the reload hint, `usage/`, `context/processor_state_recorder.py`, `context/compression_scope.py` and `context/context_utils.py` — to idiomatic Rust.
The engine is a reusable kernel service for `openjiuwen-agent`, `openjiuwen-workflow`, and `openjiuwen-harness`.
Only callers that configure a `Model` cause model calls; every LLM-backed path has a deterministic offline fallback, so compression works with no network and no credentials.
Token counting is offline by construction: a BPE vocabulary comes from `tiktoken-rs`'s embedded data or a local artefact, and a download happens only when `ContextConfig::enable_tokenizer_download` is set on a cache that is not offline.

## API Surface

Execution seams used by agents and the harness:

```rust
use std::sync::Arc;
use openjiuwen_context::{
    ContextConfig, ContextEngine, ContextProcessorStateRecorder, ContextUsageAnalyzer,
    CounterIdentity, PrepareOptions,
};
use openjiuwen_foundation::prompt::{ApproxTokenCounter, TokenCounter};

let counter: Arc<dyn TokenCounter + Send + Sync> = Arc::new(ApproxTokenCounter::new());
let engine = ContextEngine::new(ContextConfig::default())
    .with_recorder(Some(Arc::new(ContextProcessorStateRecorder::new())))
    .with_usage_analyzer(Some(Arc::new(ContextUsageAnalyzer::new(
        counter,
        CounterIdentity::approx(),
    ))));
let ctx = engine.create_context("main", session).await?;      // session: Option<Arc<dyn Session>>
ctx.add_message(BaseMessage::user("hi")).await?;              // also via ModelContext trait
let prepared = engine.prepare(&ctx, &PrepareOptions::default()).await?;
// prepared.messages (system first), prepared.usage: Option<ContextUsageSnapshot>
engine.observe(&ctx, BaseMessage::assistant("hello")).await?;
engine.observe_tool_result(&ctx, "call_1", "42").await?;
let report = engine.compress(&ctx).await?;                    // status: noop | compressed | busy
let report = engine.usage_report(&ctx, Some(1_800)).await?;   // ContextWindowTokenReport
let snapshot = engine.usage_snapshot(&ctx, None).await?;      // ContextUsageSnapshot
engine.record_provider_usage(scope, "req-1", &usage_metadata)?;
let rollup = engine.kv_cache_usage(&scope);                   // Option<SessionKVCacheUsage>
let window = engine.resolved_window();                        // ResolvedContextWindow
let change = engine.detect_window_change(&ctx);               // ContextWindowChange
let recovered = engine
    .recover_from_model_exception(&ctx, &error_text, streaming, chunks_emitted)
    .await?;
```

## Constraints

- Errors use `openjiuwen_common::error::{Error, Result}`; invalid config is `Error::Config`, bad message/window input `Error::Validation`, missing context `Error::NotFound`, malformed offload/recall records `Error::Validation`, prepare timeouts `Error::Timeout`, cancellation `Error::Cancelled`, a missing native artefact `Error::NotFound`, an undecodable artefact `Error::Validation`, an artefact model type this crate does not decode `Error::Unsupported`, and a `provider_official` source its compact code (`Error::Unsupported` on the download path, since no provider adapter exists).
- Async-first on tokio; public processors are `Send + Sync` via `async_trait`; cancellation uses `tokio_util::sync::CancellationToken`; optional per-`prepare` timeouts use `tokio::time::timeout`.
- No blocking I/O on async tasks; offload/recall/session-memory stores are async traits; locks are never held across a model call or an `await`.
- Every public data type is `serde`-serializable, `snake_case`, tolerant of unknown fields (`#[serde(default)]`), and config round-trips through JSON.
- Token counting always goes through `openjiuwen_foundation::prompt::TokenCounter`; the deterministic default is `ApproxTokenCounter`, and `TokenCounterKind::Model` resolves through the selector and falls back to an approximate counter.
- Offline-safe by construction: a context created without a `Model` still builds and runs, because only `ProcessorConfig::Summarization` requires one (`create_context` then fails with `Error::Config`); the compressor family, `FullCompact`, and `MessageSummaryOffloader` accept `None` and take their deterministic fallback, and `ContextEngine::new` already supplies an `InMemoryOffloadStore`.
- Tokenizer I/O is network-free unless `ContextConfig::enable_tokenizer_download` is set on a non-offline cache; the only other network path is the opt-in `OpenRouter` window fetch behind `enable_openrouter_model_context_window_tokens`; selection itself is synchronous and only reads the local cache, and HTTP goes through `openjiuwen_common::http::HttpClient`.
- Model calls happen only in summarisation/compression steps, `MessageSummaryOffloader`, and adaptive strategy selection; they use `Model::invoke` with `ModelRequestConfig` and never stream, and every such step falls back to a deterministic offline result on a missing model, transport error, or empty reply.
- System messages are never compressed or evicted; tool-call/tool-result pairs are never split by truncation, summarisation, or recall archiving.
- Offloaders rewrite only plain text content: an assistant message that carries `tool_calls`, non-text content, and any text that already contains `[[OFFLOAD:` are left untouched, and role/`name`/`metadata`/`tool_call_id` survive every rewrite.
- Dependencies are `base64` (a `tiktoken` `.model` vocabulary is base64 ranks) and `sha2` (artefact validation, measurement-cache keys, window fingerprints); dev-dependencies add `wiremock` (download and `OpenRouter` paths) and `tempfile` (artefact caches).
- The only process-global mutable state in this crate is the TTL-bounded `policy::global_openrouter_window_cache()`, the documented exception after the workspace `Runner`; its lock is never held across an `await` and callers inject a cache when they can.
- No `unsafe`; `tracing` only; every file stays under ~1000 lines — the largest are `processor/compressor/adaptive/strategy.rs` and `processor/rule_compression/compressors/html/extract.rs`, so split by responsibility before adding unrelated logic.

## Design Decisions

- The engine owns the default processor pipeline; a context carries an immutable pipeline snapshot created at `create_context`, matching Python's attachment-order semantics.
- `prepare` runs the pipeline on a working copy of the history and never mutates stored messages; explicit `compress` persists the changed history and reports `compressed` exactly once.
- `observe` is the add-hook seam: it appends one message, applies the rolling `max_context_messages` limit, and recomputes stats; passive processors inspect the history inside `prepare`.
- Compression triggers on `token_count > compression_threshold * effective_max_tokens`; `max_tokens = effective_max_tokens - reserve_tokens` (saturating).
- Offload handles are opaque UUIDs scoped by `OffloadScope { session_id, context_id }`, so concurrent sessions cannot read each other's payloads; markers keep Python's `[[OFFLOAD: handle=..., type=in_memory|filesystem]]` shape, and the Rust stores write no filesystem `path` (so markers carry no `path=` field).
- Token counters are stored as `Arc<dyn TokenCounter + Send + Sync>` (foundation's `TokenCounter` has no auto-trait supertraits) so processor futures stay `Send`; `ProcessorContext::counter` carries the same bounds and coerces to `&dyn TokenCounter` at counting call sites.
- Tokenizer selection is explicit spec → its native artefact → the first `compatible_fallbacks` entry (provenance `FamilyTokenizerFallback` + `target_tokenizer_unavailable`) → registry (`exact`, then unique `family` with `-_ :.` boundaries) → model encoding (`gpt-4*`/`gpt-3.5*`/embeddings → `cl100k_base`, `gpt-4o*`/`o1-`/`o3-`/`gpt-4.1-`/`gpt-5-` → `o200k_base`) → tiktoken `get_bpe_from_model` → 3-characters-per-token estimate; ambiguous family matches are refused rather than guessed.
- `TokenizerEngine::Auto` tries the native artefact first and degrades to tiktoken and then the estimate; `TokenizerEngine::Native` with no resolvable artefact still returns a working selection marked `native_tokenizer_unavailable`, because a token count stays useful.
- BPE vocabularies come from `tiktoken-rs`'s embedded data cached in `OnceLock`s and native artefacts are decoded once per selection, so model-aware counting is offline; a BPE that cannot be built degrades to the 4-characters-per-token approximation and the measurement reports `tiktoken_unavailable`.
- `TokenCounterKind::Model` uses `ContextConfig::model_name` + `tokenizer_provider` + `tokenizer_registry` + `tokenizer_artifact_manager()`; an empty configuration still yields a working approximate counter rather than an error, and verification of the contradictory `enable_tokenizer_download && tokenizer_offline` pair happens in `validate()`.
- Artefact cache layout is `<cache>/huggingface/<id>/<revision>/<artifact>` and `<cache>/models/<id>/<revision>/<artifact>`, with the name `tiktoken.model` for a `Tiktoken` engine and `tokenizer.json` otherwise; cache-dir precedence is explicit argument → `OPENJIUWEN_TOKENIZER_CACHE_DIR` → `~/.cache/openjiuwen/tokenizers` → the relative `.cache/openjiuwen/tokenizers`.
- One download per artefact is serialised by an advisory `create_new` lock marker named `sha256(source, tokenizer_id, revision, sha256, engine).lock`, with `tokio::time::sleep` backoff (10 ms → 250 ms, 10 s budget), stale removal after 120 s and removal on drop; bytes are validated (UTF-8, decodable artefact, declared sha256) and renamed from a `.<uuid>.tmp` file, so a reader never sees a partial artefact.
- `resolve` orders local `artifact_path` → on-disk `tokenizer_id` → `://` rejection → hub cache → download gate, and `provider_official` always answers `provider_official_adapter_not_configured`.
- A `tiktoken` `.model` vocabulary defaults to the Kimi pre-tokenization rule (Python's `TiktokenModelCounter`) with `PretokenizePattern::Gpt2` available; special tokens come from the sibling `tokenizer_config.json` when it declares `added_tokens_decoder`, else from the built-in Kimi map, with K3 selected when the name contains `kimi-k3`.
- Window resolution is one ladder: an explicit `max_context_tokens` wins over everything, otherwise a policy with any override resolves global cap → selected-model override → configured model map → built-in table → `OpenRouter` cache → `DEFAULT_CONTEXT_TOKENS`; a completely default policy keeps `DEFAULT_CONTEXT_TOKENS`, and `ContextEngine`/`ConversationContext` expose the result read-only.
- `OpenRouter` fetching is opt-in behind `enable_openrouter_model_context_window_tokens`; `resolve` never issues a request, `fetch`/`prefetch` return `Ok(0)` while the flag is off, and an unusable payload or transport failure is a typed error rather than a guessed window.
- The window diff is model revision → message divergence → tool signature → append → position → unchanged, and a position-only change does not invalidate the prompt cache; `prepare` keeps the last two `ContextWindowSnapshot`s so `detect_window_change` never mutates anything.
- Usage measurement is a snapshot, not a decision: the analyzer splits the window into `system_prompt`/`tools`/`skills`/`messages`, reuses one measurement per logical input, and splits a carrier by largest remainder (the remainder lands on the last fragment); `provider_input_tokens`, when supplied, is authoritative and the categories are reconciled to it.
- A fallback counter reconciles proportionally while a native counter keeps the non-message categories fixed and puts `provider_total - fixed` on `messages` (floored at 0); `reconciliation_delta_tokens` stays diagnostic, and percentages are `None` when the denominator is zero instead of `0.0`-as-unknown.
- The KV-cache aggregator is idempotent per `(scope, request_id)` and token-weighted (`read_total / input_total`); incomplete calls count as `partial` and never enter the totals, and `record_provider_usage` rejects an empty request id because it would deduplicate against every other empty id.
- The usage block on `PreparedContext` is filled only when the engine or the context carries an analyzer, and it can never fail a preparation; `usage_report`/`usage_snapshot` are the explicit calls and return `Error::Config` when no analyzer exists.
- Compression telemetry never fails a pass: the recorder logs and swallows sink, stream and measurement failures, and a missing token counter falls back to `ceil(characters / 3)` so a record still carries usable numbers.
- Phase mapping follows Python's entry points: `prepare` runs the pipeline in `get_context_window`, `compress` in `active_compress`, and `observe` runs a discarded telemetry-only pass over the appended message in `add_messages` (only when a recorder is attached); `ContextPipeline::run` defaults to `active_compress`.
- `run_in_phase` without a recorder is byte-identical to the uninstrumented loop — no clone and no task-local scope — and with one it brackets every processor pass with `started` + a terminal record inside a `with_operation` scope, so a model call the pass makes carries its operation id.
- Correlation travels in `ModelRequestConfig::extra` (`request_purpose`, `context_operation_id`) because the foundation request has no purpose field; `apply_operation` merges and `clear_from` removes, so stamping is opt-in and reversible.
- Rule compression is tier 1 of `MessageSummaryOffloader`: it runs only on that offloader's existing candidates, never on a body that already carries `rule_compressed_at`, and only above `rule_compression_max_chars`; a result that fits is kept, otherwise the summary/offload path runs on the compressed body.
- Rule-compression provenance rides message metadata (`rule_compressed_at`, `rule_compression_type`, `rule_compression_pass`, `rule_compression_details` only when truthy, `rule_compression_dump_path`) and one `[RuleCompression] applied …` tracing line per application.
- Adaptive selection must have a deterministic fallback: `AdaptiveStrategy::deterministic` walks a fixed, total ladder (no history → `noop`, stale tool results → `micro_compact`, in-flight round → `current_round`, ≥3 completed rounds → `round_level`, ≥1 completed round → `dialogue_summary`, over budget → `full_compact`, else the configured fallback), every span rung gated by `min_savings_ratio`, and a missing model, disabled flag, provider error or unparsable reply lands there.
- Adaptive is off by default and gated per compressor (`AdaptiveConfig::enabled`); when it is on, the compressor runs selection after its own trigger gate, builds the block from the `MemoryBlockPlan`, and returns a body-less `ContextEvent` naming another strategy instead of compressing it itself.
- State reinjection runs only after the benefit gate accepted a compaction, is off by default (`reinject_state`), and is a seam rather than a reader: this crate renders and trims the sections, while the skills/task/plan/team providers live in `openjiuwen-harness`.
- Each reinjected section is bounded by `state_snapshot_max_chars` and the whole message by `SnapshotRegistry::total_max_chars`; a trimmed section is marked lossy instead of being silently cut.
- Tool-result processors rewrite message content only (never remove messages), which preserves every `tool_call_id` pairing by construction.
- Summarisation replaces complete oldest dialogue rounds with one `[CONTEXT_SUMMARY]` user message, keeps every system message and the newest `recent_messages`, and never touches the most recent round.
- The compressor family shares one round model: a completed round starts at the first of a contiguous user run, includes assistant `tool_calls` and their paired tool results, and closes on an assistant message with no pending calls; system messages never belong to a round.
- `DialogueCompressor` compresses completed rounds before the keep boundary and keeps the anchor user message raw; `CurrentRoundCompressor` compresses the increment after the last user turn, clamped to a completed API round, then merges contiguous memory blocks; both are benefit-gated and never touch the newest round.
- `RoundLevelCompressor` runs a fixed ladder — per-round blocks, contiguous-block merge, an aggressive pass over the completed rounds the keep window protected, then deterministic head/tail hard truncation into one `truncated_full_context` block — every rung benefit-gated, so the history is always strictly smaller.
- `FullCompactProcessor` anchors on the last `[FULL_COMPACT_BOUNDARY]`/`[SESSION_MEMORY_BOUNDARY]` system message: the session-memory path reinjects stored notes and keeps the tail after the anchor, the LLM path summarises the active slice (deterministic `Summary:\n[i] role: ...` fallback), and the kept tail extends backwards to include a kept tool result's owning assistant message.
- `MicroCompactProcessor` is fully deterministic: it groups tool results by resolved tool name and replaces the text of all but the newest `keep_recent_per_tool` with `[Old tool result content cleared]`, never removing a message.
- Memory-block envelopes (`[DIALOGUE_MEMORY_BLOCK]`, `[CURRENT_ROUND_MEMORY_BLOCK]`, `[ROUND_LEVEL_MEMORY_BLOCK]`) keep Python's marker line, authority/instruction-status/conflict-priority lines, and `Summary:` body so a resumed Python session can read Rust-written blocks.
- Compressors and `FullCompactProcessor` archive the messages they replace through `archive_replaced_messages` only when `compression_recall.enabled` and `ProcessorContext::recall` is set, then append `[[COMPRESSION_RECALL: id=...]]` as the block's last line; a replacement rejected by a benefit gate calls `rollback_recall_archive`.
- Merge stages strip the individual blocks' recall markers from joined bodies and re-append them deduplicated, so a merged block keeps every handle exactly once.
- Recall chunking is byte-window based (`chunk_size_tokens * 4` bytes with bounded overlap) instead of tokenizer based, so it stays offline; retrieval is two-stage BM25 (`k1 = 1.5`, `b = 0.75`, ASCII/`_`-part/CJK-run+bigram tokens) with per-archive score normalisation and a skip-not-truncate token budget.
- `MessageOffloader` protects indices at or after `min(len - messages_to_keep, newest assistant without tool calls)` when `keep_last_round` is set, and resolves a tool result's name through the owning assistant's `tool_calls` (`name` or `name:glob` protection, `*`/`?` over string arguments).
- `ToolResultBudgetProcessor` re-measures the round after every offload and takes the largest eligible result (oldest on a tie) until the round fits or no candidate remains; `tool_name_allowlist = None` protects nothing.
- `ToolResultWindowProcessor` keeps one global window across all listed tools (suffix match, falling back to the message `name`); results below `min_offload_chars` are compacted in place without a store write and marked with `tool_result_window_managed`.
- `MessageSummaryOffloader` prefers its own model, then the context model, then `summarize_text_offline`; `from_configs` never fails for a missing model, and the replacement keeps `[offloaded_info]` on its own line.
- Store resolution per context is `ContextOptions` override → engine-level store (`with_stores`) → configuration default: an in-memory recall archive when `compression_recall.enabled`, and an in-memory session-memory store when the pipeline holds `FullCompact` or `MessageSummaryOffloader`.
- `enable_reload` is implemented as a prepared-window hint: `prepare` injects the English reload section after the leading system messages, only when the assembled window carries an offload marker; injection is idempotent and the hint never becomes part of stored history.
- Processor checkpoints ride the existing session seam: `ConversationContext::save_state` fills `ContextState::processors` from `ContextPipeline::save_state`, and `load_state` calls `ContextPipeline::load_state` after replacing the messages. Keys are positional in pipeline order (`name`, `name#2`, `name#3`), `Null` states are omitted, and an unknown key is ignored with a debug log.
- Counters are observability only: a processor bumps them solely when its pass really changed the working history, so a no-op run leaves the checkpoint untouched and no transform ever reads a counter.
- Window assembly applies round truncation first, then message-count truncation where system messages consume the budget, then strips leading `tool` messages (Python parity).
- A `TruncationConfig::max_tokens` below the current size acts regardless of the trigger threshold; the threshold only gates the case where no processor budget is set.
- `TruncationConfig::keep_system = false` drops the oldest system messages first, which is the only way that field is not inert.
- The context pool key is `(session_id, context_id)` with dots in `context_id` normalized to `_`, matching Python's pool identity; the context keeps its original id.
- There is no `ContextWindow`, `Compressor`, `OffloadProcessor`, or `TokenAccountant` type and no free `compress(&mut Vec<BaseMessage>)` function: the raw-history compaction seam is `ContextPipeline::run`/`run_in_phase` (or one processor's `process`), and `ContextEngine::compress` works only on an `Arc<ConversationContext>`.
- `ContextEngine` has no `Clone` and no `Default` (only `Debug`): it is shared as `Arc<ContextEngine>` — `openjiuwen-agent` holds `Arc<ContextEngine>` and rebuilds it with `Arc::new(ContextEngine::new(config))`; it is `Send + Sync` because every field is an `Arc`, a tokio lock, a `StdMutex`, or a plain value.
- The engine installs processors only from `ProcessorConfig` (`ContextConfig::processors`, or `ContextOptions::processors` per context); there is no `add_processor`/pipeline constructor, so a custom `ContextProcessor` impl cannot be attached through `ContextEngine` — `ContextPipeline::new(Vec<Arc<dyn ContextProcessor>>)` is the standalone seam.
- The processor extension surface is exactly: a config struct (`serde(default)`, snake_case), a `ProcessorConfig` variant (internally tagged `{"type": ...}`), an arm in `ContextPipeline::from_configs_with`, a re-export in `lib.rs`, and a `ContextEventKind` reuse or variant when it reports a change; `default_processors` lists only the two defaulted processors.
- `ProcessorContext` carries no session handle, so a processor persists only through `offload`/`recall`/`session_memory`/`scope`/`reinjection` and its own `ProcessorState`, which the pipeline saves and loads around the session checkpoint.
- Context state persistence is a serde `ContextState { messages, revision, processors }` stored under the session key `context` as one map of context id → state, so one session write covers every context the engine holds.
- Every offloader reports `ContextEventKind::Offloaded` with the pre-change indices, the last handle it wrote, and whole-history before/after token counts, and returns `None` when it changed nothing; `cx.manual` bypasses the thresholds, never the candidate rules.

## Deferred (Python `context_engine` features not ported)

- `provider_official` tokenizer adapters: there is no provider tokenizer API, so the source is deliberately unimplemented and resolves to `provider_official_adapter_not_configured`.
- Regex-pattern nodes: a `Split` pre-tokenizer degrades to whitespace splitting and a regex `Replace` normalizer leaves the text untouched, both with a recorded warning, because this crate has no `regex` dependency.
- The `NFC`/`NFD`/`NFKC`/`NFKD` (and `Nmt`/`Precompiled`) normalizer families: no Unicode-normalization dependency offline, so they are skipped with a warning and the text stays unnormalized.
- Full `HuggingFace` Unigram parity (`byte_fallback` interactions, `unk_id`/`user_defined` symbols, BPE dropout, `fuse_unk`), which is reduced to a forward dynamic program with a fixed unknown penalty and explicitly documented approximations.
- Python's host-specific reinjection builders (`processor/forked/compressor/reinjection/builders.py`: plan file, skills, touched files, task status, team snapshot, todo list, plan mode, tool-result hints): those readers live in `openjiuwen-harness`, and this crate provides only the `ContextSnapshotProvider` seam.
- Python's LLM-driven session-memory agent (`session_memory_agent.py`: `agent_edit`/`direct_replace` note extraction, pending-file commit); Rust takes notes from `SessionMemoryStore` and keeps Python's `PrefixCompactProcessor`/`SessionMemoryCompressor` behaviour under its own processor names.
- The rule-compression gaps listed in `./src/processor/rule_compression/CONTEXT.md` (`json_repair` grammar, readability ladder, Unicode sniffing, workspace dump directory, Python's strategy switch).
- Python's shared JSONL debug-record writer (`processor/forked/support/context_debug.py`: threshold checks, span splits, compression retries, before/after diffs and the ReAct outbound payload): Rust emits rule-compression JSON dumps and `tracing` records instead.
- Python's compression-artefact dumps (`processor/forked/compressor/support/compression_dump.py`: one JSON file per compaction with input/output messages and benefit, plus `OPENJIUWEN_COMPRESSION_DUMP_DIR` template expansion): Rust keeps compaction history in `ProcessorState` and `tracing`.
- Python's structured compression-error taxonomy and classification (`CompressionExecutor`/`CompressionErrorKind`: `context_overflow`, `rate_limit`, `authentication`, `timeout`, `server_unstable`, `api_request_error`, `unknown`): Rust treats any compression model failure as a trigger for its deterministic fallback.
- A `ModelRequestConfig` purpose field: correlation is carried in `extra` under `request_purpose`/`context_operation_id` because the foundation request type has no purpose field.
